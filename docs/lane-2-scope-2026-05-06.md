# Lane 2 Scope — Lead Lifecycle Reset + Compaction Accounting

**Date:** 2026-05-06
**Owner:** claude-principal-software (Lane 2A: trigger + rehydration), codex-performance (Lane 2B: accounting + measurement)
**Constraint:** Do not touch `server/src/orchestration/session-policy.ts` (owned by Lane 1, codex-performance)

## Context

Locked plan from research mission: leads accumulate provider amplifier across turns until `/compact` fires; each `/compact` is durable-memory churn that itself burns tokens. The fix is to reset the lead session *before* `/compact` pressure, deterministically, and rehydrate the fresh lead from existing Mission Control state (no new lossy summaries). All four turn classes (`normal.turn`, `maintenance.compaction`, `workflow.repair`, `post-reset.first-turn`) must be classified at write time so Lane 2B's measurement queries can attribute spend correctly and prove the ≥25% gate without averaging cache-miss costs into the win.

## Sub-deliverable 1 — Deterministic reset trigger

**Two trigger paths, both fire `reset-session` (the action already exists):**

1. **Phase-boundary trigger.** Hook into the existing `autoAdvancePhase` callback wired at `server/src/broker.ts:4714`. When a phase advances, schedule a lead-only reset for the room's `leadAgentId` to fire on its next dispatch. New helper: `scheduleLeadResetOnPhaseBoundary(roomId, leadAgentId)`. Stored as a one-shot flag in a new in-memory map (or a `pending_lead_reset` row keyed by `(room_id, agent_id)` if we want survival across server restart — recommend in-memory for v1; restart loses the pending reset which is recoverable).
2. **Pre-compact-pressure trigger.** Extend `autoContextMaintenanceDecision` (`server/src/orchestration/auto-compaction.ts:62`) to take a new `isLead: boolean` input. For leads, lower the reset threshold to `LEAD_RESET_PERCENT` (default 60% of the compact threshold, env-overridable via `FIRESIDE_LEAD_RESET_PERCENT`) and emit `action: 'reset-session'` instead of `action: 'compact'`. The existing `/compact` path remains as a backstop for non-lead resumed turns and any escape hatch where Lane 1's defaults are explicitly overridden to `compacting` for a worker.

**Acceptance:** A lead never reaches the `/compact` threshold under normal operation. The legacy `/compact` path remains compiled and tested (backstop), but ceases to fire on the lead in a healthy room.

## Sub-deliverable 2 — Bounded rehydration checkpoint

**Schema (cap ~3-5k tokens, all sourced from existing state, zero new lossy summarization):**

```typescript
interface LeadRehydrationCheckpoint {
  missionGoal: string;                        // from active mission
  currentPhaseId: string | null;              // from currentMissionPhaseId
  planExcerpt: string;                        // active plan latest revision, truncated to N chars
  openChecklist: { id: string; status: string; note?: string }[];
  recentlyResolvedChecklist: { id: string; status: string; note?: string }[];  // last K=5
  recentCouncilDecisions: { kind: string; summary: string; at: number }[];      // last K=5
  blockers: { id: string; reason: string }[];
  recentWorkerOutcomes: {                                                       // last K=3 per worker
    agentId: string;
    runId: string;
    status: string;
    runKind: string;
    at: number;
  }[];
}
```

**Rendering.** New module `server/src/orchestration/lead-rehydration.ts` exports:
- `buildLeadRehydrationCheckpoint(db, roomId): LeadRehydrationCheckpoint`
- `renderLeadRehydrationBlock(checkpoint): string` — formats as a hidden Mission Control–style block, wrapped in `/lead-rehydration … /end-lead-rehydration`. Hard-truncated to ~4k tokens (≈16k chars) before return; truncation drops oldest worker outcomes first, then oldest council decisions, then plan excerpt tail.

**Injection.** When the broker dispatches a turn whose `(roomId, agentId)` has a consumed pending reset, prepend the rendered block to the agent's prompt construction in `server/src/orchestration/agent-turn-context.ts`. The existing `roomLeadAgentId` is already in the input shape there.

## Sub-deliverable 4 — First-turn-after-reset metric

Already covered by sub-deliverable 3: `run_kind = 'post-reset.first-turn'`. The metric Codex needs is: provider tokens for that bucket vs. average for `normal.turn` on the same agent. The bucket exists; the query is Lane 2B's job.

**Single hard requirement from this lane:** every consumed pending reset MUST result in exactly one `post-reset.first-turn` outcome on the next successful dispatch for that `(room, agent)`. If the dispatch fails or is canceled, the pending-reset flag stays set so the next dispatch carries it. Tested in the integration test from sub-deliverable 2.

## Sub-deliverable 5 — Fidelity test plan

The five guards from the locked plan, each with the test surface that proves it:

1. **Mission outcome rate.** Soak metric, not unit-testable. Codex tracks pre/post mission completion rate from the same DB. No code from Lane 2A.
2. **Repair-trigger rate.** Soak metric on `agent_turn_outcomes WHERE run_kind = 'workflow.repair'` count per mission, before/after rollout. No code from Lane 2A beyond the `run_kind` write.
3. **Receipt compliance.** Soak metric. Codex query — count of `/mission-receipt` and `/mission-task` blocks per dispatched turn, before/after.
4. **Post-reset coordination cleanliness.** Soak metric, queryable from `collab_notes` (or wherever they're stored — confirm in Lane 2B query): zero notes flagging missing/malformed context in N=3 turns following any `post-reset.first-turn` outcome. Lane 2A does not gate on this; Codex's measurement does.
5. **Decision consistency A/B (optional).** Paired-mission harness running the same brief twice with reset-enabled vs reset-disabled; manual diff of final mission outcomes by inspection. Lane 2A provides a feature-flag to disable the deterministic reset (env var `FIRESIDE_LEAD_RESET_DISABLED=1`) to make this harness possible. Otherwise no Lane 2A code.
